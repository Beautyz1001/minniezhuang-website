## [2026-09-09] 缩短「视频到 WORKS」空白：先误解需求、又用错技术方案

- 尝试方案（第一次，理解错）：用户说"缩短视频和 WORKS 的间距"，我理解成"把
  WORKS 这一个字单独往上挪 150px"，做法是给 `.works-sticky-word` 的
  `margin-top`/`margin-bottom` 各减/加 150px。
- 用户反馈："我的意思其实不是把 works 往上面移动，而是把这两个部分之间的
  间距减少……把 works slogan 和底下的所有部分都当作一个整体上移。"
- 判断：**用户要的是整体平移，不是单独挪一个元素。** 只挪 WORKS 会把它和
  slogan 之间原本 130px 的间距拉大到 280px，破坏了内部关系。
- 尝试方案（第二次，方向对了但技术选错）：改成给 `.home-works` 加
  `margin-top: -150px`，指望把 WORKS+slogan+卡片当整体一起移动。
- 现象：**实测完全无效**——`.home-works` 和父级 `.inner-world` 的位置分毫不差。
  用 JS 把这个 margin-top 从 0 一路调到 -5000 逐档测过：小于 -2115.92px
  （`.inner-world` 自己那条 JS 算出来的抵消门洞 pin 高度的负 margin-top）
  时完全不动，超过之后才开始联动。
- 判断：**触发了外边距塌陷（margin collapsing）**。`.home-works` 是
  `.inner-world` 的第一个子元素，两者的 `margin-top` 会塌陷合并成更负的那个，
  `-150` 比 `-2115.92` 小，直接被吃掉。**原以为 `.inner-world` 的
  `overflow: clip` 能挡住父子塌陷——实测完全挡不住，这条判断作废**，
  以后不能再假设 overflow 非 visible 就一定安全。
- 结论（当时，第二次）：**父子之间用负 margin 做位移不可靠，塌陷会被无关的更大数字吃掉，
  改用 `transform: translateY()` 才对**——transform 不参与文档流、不会塌陷。
  但 transform 也不会带动后续兄弟一起移动，需要额外配一条
  `margin-bottom`（**兄弟间**的塌陷是可预期的，不会被吃掉）把这段距离
  还给文档流，兄弟元素才会跟着一起上移。
- **⚠⚠ 后续（同日，第三次）：上面那条"改用 transform"的结论是错的，已作废，
  而且这一版直接上线过，被用户发现"WORKS 的固定动效怎么没有了"。**
  尝试方案（第二版）：`.home-works` 加 `transform: translateY(-150px)` +
  `margin-bottom: -150px`。数值全部正确（间距缩短 150、内部关系不变、
  黑色底图渐变没受影响），**但 `.works-sticky-word`（`position: sticky`）
  是 `.home-works` 的子元素**，一旦祖先有 `transform`，浏览器会给它建立
  新的 containing block，`position: sticky` 的吸顶行为需要一路找到
  "最近的滚动容器"，中间插一层 transform 建立的 containing block 就会把
  sticky 限制在那个盒子内部，直接**失效**（不再跟随视口滚动）。
  这是纯 CSS 规范行为，不是浏览器 bug，**任何时候要给一个包含 `position:
  sticky` 元素的祖先做位移，transform 都不能用**。
- 最终结论（第三次，真正对的）：位移拆成两条**都不碰 `.home-works` 自己**的 margin——
  sticky 元素（`.works-sticky-word`）自己的 margin-top/-bottom 各减/加同一个数
  （净位移不变，只挪它自己）；它的**非 sticky 兄弟**（`.works-intro`）直接加
  `margin-top: -X`（`.home-works` 有非零 padding-top，父子margin 不会塌陷，
  这条 margin 正常参与文档流，会带着 `.works-grid` 和后面的 Break/VR/Footer
  一起上移）。**以后「一整块内容（含 sticky 元素）连同兄弟一起挪」，
  不要在共同的父级上做任何 transform 或 margin，要分别在 sticky 元素自己
  和它的非 sticky 兄弟身上各自处理位移。**

## [2026-09-04] 正面墙 / 门洞写实

- 尝试方案：把原本隐形的正面墙做成可见的受光表面——真几何起伏 + 大尺度污渍 +
  真立体门套 + 踢脚线，另加一盏"地面反弹光"从下方打亮墙面。
- 用户反馈：「我不行了，怎么这么丑，你跑了20分钟，怎么搞出来这么丑的东西啊」
- 判断：
  1. **用聚光灯照墙是错的方法。** 聚光灯在墙上打出的是一团有边界的光斑／横向亮带，
     读起来是"墙上有一片光晕"，不是"这面墙被照亮了"。参考图里墙的亮度是连续铺开、
     没有可辨认光源形状的。用一盏灯去模拟漫反射反弹，方向本身就不对。
  2. **墙根那条横向亮带是这个构图的必然产物**，不是调参能解决的：
     单面平墙 + 正面平视 + 从下打光 = 一条水平亮带。参考图靠两侧墙和透视打断它。
  3. **流程错误（更重要）**：第一版截图明显难看时就该停下来给用户看、问方向，
     而不是连调七八轮参数再交付。用"位移改变了 230 万子像素"这类技术指标去证明
     效果成立，是拿错了尺子——用户只看好不好看。
- 结论：这套"可见墙 + 反弹聚光灯"整体作废。以后要让墙显形，必须换一种照明思路
  （不是换参数），并且**先出一版最小效果给用户看**再往下做。

  （静帧或短循环视频），色彩沿用 #C30750 这套。

## [2026-09-04] 首屏标题的入场方式

- 尝试方案：标题整行上抬 + 两个词各自用 `clip-path` 从底部擦入（遮罩擦除）。
- 用户反馈：「现在这个入场动画是 OK 的但是没有达到惊艳的效果，我希望是非常电影质感的
  入场，比如文字可以是从中间模糊的入场逐渐清晰这样」。
- 判断：遮罩擦入是**平面动作**，它只说明"字出现了"，说明不了"镜头找到了它"。
  这类几何遮罩（擦入、逐字翻出、字符错位）对这个站都偏"网页动效"，不是电影感。
  电影感来自**镜头的物理行为**——对焦、曝光、景深。
- 结论：标题入场改为一次合焦（虚→实 + 略大→正 + 过曝→正）。
  以后要给首屏文字做入场，先想"镜头在做什么"，不要再从遮罩形状入手。

## [2026-09-04] 首屏标题入场（第二次修正）

- 尝试方案：整行统一合焦——全行同时从虚变实、从略大收到正。
- 用户反馈：「我的意思其实是，底下的字是从中间开始向两边展开显示，
  先出现中间，再浮现两边」。
- 判断：**误读了"从中间"。** 用户说的"从中间模糊"指的是**位置**（从画面正中开始），
  不是"整体虚化"。整行同时合焦是没有方向的，读起来是一整块在变清晰，
  和"从中间往两边长出来"完全是两回事。
- 结论：主动作必须是**横向从中心往两侧展开**（边缘羽化，两端最后浮现），
  合焦只能当配角、量要压小。以后用户描述动效时提到方位词（中间／两边／上下），
  优先按**空间顺序**理解，不要先往材质（虚实、明暗）上想。

## [2026-09-05] 加载动效的进度条

- 尝试方案：灰色轨道 + 洋红填充条 + 从左往右填满，底下一个百分比数字。
- 用户反馈：「现在这个进度条太土了，换一下，更高级一些」。
- 判断：这是软件安装进度条／游戏读条的标准长相，三个特征全中：
  1. **有一条等着被填满的灰轨道**——"未完成"被画成了一个可见的空槽；
  2. **从左往右长**；
  3. **两端是切齐的方角**。
- 改法（三条都是"把控件变成光"）：
  1. **去掉轨道。** 没加载到的地方就是黑的，光只存在于它已经到达的地方。
     这条是"土/不土"之间最大的分界。
  2. **从中心往两边长**，长度本身就是进度。方向和标题展开、门洞对称是一套语言。
  3. **两端用遮罩化开**，光没有方角。变成门洞时再把虚化收到 0（门洞得是硬边）。
- 长期结论：这个站里凡是"进度／状态"类的东西，先想它在这个空间里是什么光，
  不要先想它是什么控件。轨道、方角、左起点，都是控件的签名。

## [2026-09-05] 加载→入场的衔接（连改三次才找到根因）

## [2026-09-05] 大标题 hover：用"照亮"替代"变粗"

## [2026-09-09] ⚠ 验证滚动效果时用 `window.scrollTo`（方法错误，代价最大的一条）

- 尝试方案：验证任何滚动相关的效果时，用 `window.scrollTo(0, y)` 把页面滚到某个位置，
  再读元素的样式/位置来判断动效对不对。
- 现象：量出来整站的滚动动画**全部停在原地**。据此得出过一串错误结论——
  「参考站没有入场动画」「我们的图片位移根本没在跑」「NBA2K 那格的触发器不执行」，

- 结论（长期有效）：
  1. **验证滚动效果只能发真实滚轮事件**（Chrome 扩展的 `computer` scroll）。
     滚轮走的是 Lenis 的正常通路，`--cam-depth` 之类的量会跟着动，才是真的。
  2. 只是想读某个静态数值（框多宽、素材多大）不受影响，随便读。
  3. `ScrollTrigger.getScrollFunc(window)(y)` 能驱动 ScrollTrigger，
     但**驱动不了门洞那套自己的滚动映射**，两边会脱节，量出来更乱。用过一次，别再用。
  4. ⚠ **发现"动效没生效"时，先怀疑测量方式，再怀疑代码。**
     今天连着三轮把好代码判成坏的，最后还据此把功能删了，用户原话
